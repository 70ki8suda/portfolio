# このブログの日本語執筆・推敲

読者が内容を理解しながら、無理なく先を読める文章を書く。情報を薄めて短くするのではなく、説明の順序、言葉、文と段落の呼吸を整える。

このスキルは humanizer-jp の編集方針をブログ向けに再構成したもの。特定の作家へのなりきりや固有の文体の再現は行わない。作家名による要望は、平易さ、落ち着き、リズム、具体性、比喩の節度という一般的な品質に置き換える。AI判定器の回避や、人間が書いたという表示を目的にしない。

## 優先するもの

1. 元の主張、根拠、条件、情報量を保つ。
2. 誰の発言・解釈なのかを明確にする。
3. 読みやすい順序と自然な日本語に整える。
4. 必要なところだけ、リズムや比喩を調整する。

美しい言い回しと正確な説明が衝突したら、説明を取る。編集対象以外の機能やデザインには作業を広げない。

## 中心の問いとメタデータ

- 全文を読み、記事が主に答える問いを一文で捉えてから、title・description・tagsを照合する。タイトルは主題を先に置き、説明文は資料の範囲と筆者の比較・解釈を区別する。本文でできていない検証や原典の精読を約束しない。
- 記事タグは、まとまった説明や比較のある主題を根拠に選ぶ。一度出る単語、関連させたい思想、シリーズの統一感だけを理由に付けない。適切な既存タグは、変更件数を増やすために入れ替えない。記事タグと段落グラフの概念タグは別々に判断する。
- 記事タグは同じ問いを扱う別記事への入口にする。人名・書名・運動名はtitleや本文検索で足りるなら使わず、独立した節か全体を通した議論のある主題を選ぶ。1記事2〜4個を目安とし、主題の根拠があれば超えてよい。
- 1記事だけのタグは原則つくらない。ユーザーが指定した主題、音楽などの記事の種類、継続して扱うと決めた主題は例外とする。記事数を増やすための過剰付与はしない。
- 意味の広い語は対象を区別する。権限・設備・技術の分散と地方での暮らしは「権力の分散」「地方分散」、AIの社会的影響と投資の採算は「AIと社会」「AI投資」のように分ける。時事記事にも対象と検証方法が分かるタグを付ける。
- ソーラーパンクなどへの接続は、比較する軸と本文上の根拠があるものを残す。無理な導入や結びだけを整理し、有意義な比較、本人の所感、用語、情報量を一緒に削らない。選曲や作品への個人的な受け取り方を、ジャンルの客観的な分類や作り手の意図に変えない。
- 複数の媒体を扱う入門では、資料や動画ごとの紹介を並べる前に、共通する問いで構成する。宣言、評論、フィクション、広告、現実の実践を区別し、誰が何を提案したかを近くに示す。翻訳・リミックスの宣言を唯一の公式定義にしない。既存の有用な説明と埋め込みは保つ。

## 語り口

- 基本は落ち着いた「です・ます」。読者と同じ高さから説明し、教師のように理解を促したり、感動を指示したりしない。
- 短い文は、説明を区切るために使う。条件や因果が複雑な箇所は長くてもよい。長短を機械的に交互にしない。
- 一段落に一つの話題を置く。段落の末尾を毎回、教訓・名言・問いかけで締めない。説明が終わったら、そのまま次へ進んでよい。
- 抽象語より、誰が何をするかを書く。具体的な人・物・行動は原稿や資料にあるものを使い、リアリティのための細部を創作しない。
- 比喩は仕組みの理解を助けるときに限る。比喩を外したら何も残らない文は、説明から書き直す。既存の仮定例は条件を残す。
- 一人称や感想はユーザーが述べた内容、または元原稿にある声を尊重する。架空の思い出、生活習慣、読後感、文学的な人物像を追加しない。
- 慎重な留保は残す。「予測」「仮定」「本人の見方」を、文章の勢いのために確定した事実へ変えない。

## humanizer-jpから引き継ぐ編集判断

次の傾向を文脈ごとに点検する。禁止語リストとして一括置換しない。

- 「本記事では解説します」「まず見ていきましょう」など、内容の前に置かれる進行説明。
- 「重要なのは」「本質は」「大きな一歩」など、理由のない評価や意義の水増し。
- 「単なるXではない。Yだ」の反復、無理な三点セット、すべての段落に同じ型を当てる書き方。
- 「時間の厚み」「未来への入口」など、何を指すのか説明できない抽象的な比喩。
- 「することができます」などの冗長な述語。同じ主語・語尾・接続詞の連続。
- 本文を言い換えただけの小見出しや結論、説明のあとに付く不要な褒め言葉。
- 短い断定や体言止めを連打する広告調のリズム。

正確な専門用語、機能的な表や箇条書き、主張と補足を分ける見出しは残す。文法の一貫性や特定の句読点だけを理由に直さない。原典のダッシュ禁止などは機械的に適用せず、引用・作品名・リンク・メタデータを守る。

## 既存記事の推敲

- 対象記事を全文読み、章ごとの主張、具体例、数値、留保、出典を把握する。長文は分割して読み、冒頭だけを見て全体を置換しない。
- 下書き、内容照合、文章の読み直しを内部で行い、ファイルには最終稿だけを残す。
- 論点・事例・数値の条件を削って要約版にしない。同じ情報の繰り返しや進行説明は整理してよい。文字数そのものを品質目標にしない。
- 動画の主張、筆者の考察、仮定の数値例を混ぜない。前置きを省くなら、見出しや近くの文で区別が残ることを確かめる。
- frontmatter、URL、明示アンカー、YouTubeのコードフェンス、表の数値は維持する。変更が必要なら、依頼の対象かを確認し、目次や参照箇所も一緒に扱う。
- Garys Economicsの統合記事では、14本分の説明・例・注意点を保つ。時事動画は収録時点の認識や予測として扱う。
- ソーラーパンク記事では、3人の一致点と意見の違いを残す。サイトの水耕栽培の風景についての筆者の考察を、動画の発言や実証済みの性能と混同しない。

## 新規記事の執筆

- 指定資料を確認してから構成する。資料を取得できない箇所は、確認できたかのように補わない。
- 冒頭は、記事で説明する具体的な疑問や状況から入る。読後の効用を約束する宣伝文を置かない。
- 節の数や構造は内容に合わせる。「定義・メリット・課題・未来」などの型を先に押し付けない。
- 新しい具体例を作る場合は仮定であることを示し、実際の出来事や話者の例として紹介しない。
- 出典と動画埋め込みは既存記事のMarkdown形式に合わせる。全文翻訳や逐語的な再構成ではなく、論点を自分の構成で説明する。

## 編集例

以下は本スキル独自の例。特定の作家の文章を模したものではない。

**進行説明を内容に替える**

前：ここからは、お金と実物資源の違いについて詳しく見ていきましょう。

後：お金を配っても、会場の座席は増えません。

この書き換えは、前後ですでに席数が固定された会場の例を置いている場合に使える。資料にない設定を勝手に足さない。

**比喩より作業を書く**

前：手入れの時間の厚みが、未来の風景に命を吹き込みます。

後：植物は育ちます。水やりや剪定も続きます。その作業を誰が担うかは、完成予想図からは分かりません。

**慎重さを削らない**

前：Garyの予測は、格差の拡大が経済を必ず崩壊させることを示しています。

後：Garyは、格差が広がれば生活水準は下がり続けると予測します。この動画だけで、その予測が正しいとは確かめられません。

## 最終確認

元原稿と差分を照合し、論点や条件の欠落、話者の取り違え、新しい事実の混入がないかを確認する。次に文章として通読し、説明の重複、不自然な文の切れ目、装飾のための比喩を直す。

記事を更新した場合は、目次のリンク先、動画、表、表示を変更リスクに応じて確認する。確認できた範囲と変更点を短く報告する。依頼がスキル作成だけなら、既存記事の再編集は行わない。

## 執筆・改稿後のグラフ分類

記事を新規作成したときや本文を変えたときは、執筆を完了する前に[段落グラフの運用手順](../../../docs/content/paragraph-graph.md)を読み、編集メタデータと生成物も更新する。通常一覧への公開可否は `draft`、長く育てるテーマの地図への適格性は編集分類で別々に判断する。分類だけを理由に公開・非公開を変更しない。

記事本文を書いたAIが、公開前までに次の一連の処理を自分で完了する。人に分類ファイルの作成を依頼して終わらない。

1. 記事の追加・改稿・削除・公開状態変更後、`npm run graph:update -- --request /tmp/graph-update-request.json` を実行する。変更を検出し、判断が不要なら分類とのopt-in整合、孤児タグの除去、差分embedding、JSON生成と検査を自動で行う。
2. AI判断が必要と出たら、requestの対象記事を**全文読み**、表・箇条書き・前後の文脈も確認する。requestの`replyShape`に従って `/tmp/graph-update-reply.json` を自分で作る。`requestHash`と各`sourceHash`をそのまま返す。`articles`は要求されたslugだけを過不足なく含める。
3. 本文の主目的からcategoryとdecision、具体的なreasonを記す。`long-term`は所有・暮らし・思想・技術と社会などを後から問い直す概念探究で、概念段落があればinclude。`current-affairs`は特定時点の出来事・企業・相場を判断する記事、`curation`は概念論のない選曲・紹介、`other`はそれ以外で通常exclude。判断しきれない場合は`uncertain`/`review`。単語・slug・日付で代用しない。
4. 有効判断がincludeになる記事は、requestの**全段落**を読んで`paragraphs`へ記す。採用段落は既存概念1〜3個、`stance`（source/author/critic/mixed）、具体的な話者・仮定・留保を示す`context`。案内・出典・表や箇条書きへの依存した導入は`tags: []`と`excludeReason`。本文が同じ段落も周囲が変われば判断し直す。必要な新概念だけ定義付きでreplyの`concepts`へ追加する。既存概念の上書きはしない。
5. 人のoverrideはrequestのpreviousから読み、有効判断を優先する。replyにoverrideを含めたり、既存の人の判断を消したりしない。excludeの記事は`paragraphs: {}`とする。reviewは人の明示overrideがない限り**公開を停止**する。成功させるために全記事を除外しない。
6. `npm run graph:update -- --request /tmp/graph-update-request.json --reply /tmp/graph-update-reply.json` を実行する。分類・対象記事のgraphフラグ・段落タグ・ローカルembedding・公開JSON・鮮度検査まで同じ入口が行う。古いrequest、欠落判断、環境不備、競合は停止するので原因を読み、必要な判断だけやり直す。ハッシュだけの差し替えで通さない。
7. 運用手順の対象テストと表示確認を行う。新旧ノード・関連候補を読み、話者の取り違えや弱い接点を確認する。本文と判断・生成物を同じcommitに含める。`npm run build`もこの入口を呼び、未判断や不整合があれば公開用buildを止める。

これはAPIや新しい課金契約を使う自動分類ではない。執筆AI自身の全文読解を、ハッシュに束縛した構造化出力で機械工程へ渡す。AIがいないbuildでは必要判断が明示される。下書きは公開・地図から除外され、公開に変える際に最終本文で判断する。通常の記事公開とグラフ適格性は別だが、未決着の分類を黙って除外して公開しない。

記事全文vectorは採用段落とは独立して更新されるため、表・箇条書き・末尾だけの変更でも同じ入口を使う。通常更新は共通の固定基底を保持する。基底欠損やrecipe不一致を通すために無断で`--refresh-projection`を付けず、欠損・破損を調べる。意図した全体再配置では明示refresh後の座標差分と近傍を監査する。

詳細な返信例、ロック・失敗時の復旧、Python環境は[段落グラフの運用手順](../../../docs/content/paragraph-graph.md)を参照する。

### 下書きの扱い

下書き中の分類は任意。公開前に `draft: false` の最終本文で `graph:update` を呼び、必要なrequestをAI自身が読んでreplyを生成・適用する。公開状態もハッシュに含まれる。下書きの `graph: true` は公開資格を与えず、本文・タグ・ベクトルは地図へ出ない。
