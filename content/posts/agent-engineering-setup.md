AIエージェントにコードを書かせると、量は増えます。困るのは、その量を人が確かめきれないことです。Lauren Tanさんは、2026年11月の講演で、エージェントを訂正するたびにプロンプトの注意書きを足すのをやめ、コードベースそのものを直すという方針を説明しました。本人が公開している設定一式「pstack」には、その方針を日々の作業に落とした手順が書かれています。

講演で示された考え方と、pstackのREADMEおよびガイドに記された手順を整理します。

## 誰の、どんな講演か {#talk}

講演の題は「All Code Is Slop (Except Mine)」です。直訳すれば「コードはぜんぶ粗悪品（私のを除いて）」。AI Engineer Code Summitで行われ、主催者のYouTubeチャンネルで2026年11月14日に公開されました。17分半ほどの講演です。

話者のLauren Tanさんは、potetoという名前で活動しています。講演の冒頭では、SpaceXSIでGrok Botに携わっていると自己紹介しました。主催者の字幕では、肩書きはPrincipal Engineerです。pstackのREADMEには、Meta、Netflix、Cursorで働いてきたこと、Reactのコアチームの一員としてReact Compilerの開発に関わっていることが書かれています。講演には、Cursorで経験した失敗の例と、Grok Botでの現在のやり方の両方が出てきます。

講演の主張は、最初の数分にまとまっています。Tanさんは前の月に、自分で約3,000件のプルリクエスト（PR）を本番に出したと述べました。エージェントを使えば誰でも大量のコードを出せる。だからソフトウェアエンジニアの仕事は、生産性を大きく上げながら、コードの品質を保つか、むしろ上げる方法を見つけることになった、というのがTanさんの考えです。その鍵は信頼だと言います。エージェントを盲目的に信頼するのではなく、エージェントが正しいことをすると信頼できるように、エージェントの働く環境に投資する、という意味です。ここまで来るのに6か月かかったとも述べています。[講演：0:31〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=31s)

## 信頼の逆三角形 {#pyramid}

どこに時間を使うかを、Tanさんは逆三角形の図で示しました。上の層ほど広く、先に手を入れるところです。

| 層 | 中身 | 性質 |
| --- | --- | --- |
| コードベース | APIの設計、アーキテクチャ、リファクタリング | 判断に頼らない制約。コードそのものでエージェントの行動を絞る |
| 静的解析 | lint、型、コンパイラ、各種のテスト | 判断に頼らない制約。検査として書いた規則への違反を機械的に止める |
| 検証 | 実行時の検証、形式検証 | バグを見つけ、成り立つべき性質を確かめる |
| 文章 | ルール、skill、AGENTS.md | 判断が要ることだけを書く |
| 人のレビュー | 最後に残るもの | 最も狭い |

Tanさんは、上の二つの層を、判断に頼らない決定的な制約として位置づけています。この二つでエージェントにできることを絞り、何もしなくても正しいやり方になるようにする、と説明しました。文章で書く指示は、判断が必要なことのために少しだけ重ねます。[講演：2:03〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=123s)

指示の文書を書き、足りないところをまた文書で補っていくやり方とは、順序が逆です。Tanさんの図は、文書を最後から二番目に置いています。

## コードベースは、エージェントへの最大の入力 {#codebase}

エージェントの出力は、入力で決まります。そして、入力の中で最も大きいものの一つがコードベースです。Tanさんはここから、訂正のしかたを導きます。エージェントを訂正するとき、ルールやAGENTS.mdに一行足す前に、それを決定的な検査にできないかを考える。コードになっていれば、同じ結果が再現され、信頼できるからです。スライドには「code is memory」（コードが記憶である）とありました。[講演：3:01〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=181s)

Tanさんはコードベースを庭にたとえます。2024年には、出社して同僚のPRを3件ほどレビューしていた。いまはその数が300件ほどになった。コードは途切れない流れのように届き、生き物のように育つ。エンジニアが置く制約やガードレールは、その成長を支える土台にあたる、という説明です。

庭には雑草も生えます。回避策、よくない書き方、古くなったコード、技術的な負債は、次のエージェントにコピーされます。そのコードベースで確立された書き方に見えるからです。一度コピーされると、次にコピーされる確率がさらに上がります。だから、エージェントがいつもよい例をコピーするように、コードベースをできるだけきれいに保つ、というのがTanさんの方針です。

講演では、具体例が四つ挙げられました。

**細かな判断が要るものは、禁止する。** Grok Botのチームは、Duneというクライアント用の枠組みを作りました。Tanさんによれば、技術的に目新しいものではなく、Electronアプリ向けのNext.jsのようなものです。特徴は、デスクトップアプリを作って学んだ教訓を、制約とlintの規則として組み込んであることです。たとえばReactのuseEffectは、正しく使うのに細かな判断が要り、エージェントは上手に使えません。そこで製品のコードでは使用を禁止し、Duneの内部のごく一部でだけ許可しました。Tanさんは、この種類の問題はまるごとなくなり、コードレビューで見つける必要もなくなった、と述べています。[講演：5:00〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=300s)

**ディレクトリの構造で文脈を伝える。** Tanさんによれば、ElectronアプリであるCursorでは、エージェントがメインスレッドのコードを画面を描く側にimportすることがよくあり、動作が重くなる原因になりました。Grok Botでは、最上位に二つのディレクトリを置き、相互のimportを依存グラフの解析とlintで禁止しました。スライドには、型のimportも不可で、共有する型は別のディレクトリに置く、と書かれています。[講演：6:00〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=360s)

**応急処置は広がる。** Cursorでは、エージェントがsetTimeoutのようなタイマーを応急処置として好んで使いました。背景には、VS Codeの命令的な書き方と、Reactの宣言的な書き方の食い違いがありました。スライドの時系列では、9月9日にちらつきを直すためのタイマーが一つ入ります。エージェントは、根本から直すと大きな変更になる、と理由を述べていました。10月3日には共有モジュールにコピーされ、10月17日にはタイマーが183個になっていました。アプリの動作は重くなりました。[講演：7:20〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=440s)

**コメントは逃げ道になる。** タイマーの例でいちばん悪かったのは、応急処置がなぜ正当かを説明するコメントを、エージェントがたくさん書いたことだとTanさんは言います。Grok Botでは、コメントの99％を禁止しました。理由は四つです。コメントはすぐ古くなる。人はあまり読まない。エージェントに、難しい正しいやり方を避ける言い訳の場所を与える。そして、強制できない。次のエージェントに「これをするな」と書き残しても、信頼できるものにはならない、という指摘です。スライドの棒グラフでは、7月31日に約6万6千あった数が、講演の時点で約1,200になっていました。コメントに限らず、エージェントは文書やルールにも言い訳を書き、小さな訂正を絶対の規則のように扱うことがある、ともTanさんは述べています。[講演：8:15〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=495s)

## 訂正を、検査に変える {#correct}

四つの例に共通する原則を、Tanさんはこうまとめました。エージェントを訂正するたびに、それを決定的な検査に変える。あるいは、APIの設計やアーキテクチャを改めて、その種類の問題が起きないようにする。lintの規則には、根本の原因を直すよう伝える、役に立つエラーメッセージを付ける。これを繰り返すと、コードレビューで気をつけることが減っていく。やがて見るものがなくなり、エージェントが自分のPRの大半を自分でマージできるようになる、という見通しです。[講演：9:01〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=541s)

pstackには、この原則を手順にした`/correct`というskillがあります。前提として置かれているのは、かなり悲観的な想定です。すべての貢献者はエージェントで、自分が開いたファイルしか見ず、いちばん近い例をコピーし、コンパイルが通る最短の道を選ぶ。その前提で、一つのファイルから見て正しそうな変更が、リポジトリ全体でも正しくなるように設計する、と書かれています。

手順は次のとおりです。

1. 最近のコミット、取り消されたコミット、レビューのコメント、エージェント向けの指示ファイル、回避策を説明するコメントを読み、間違いを種類に分ける。二度起きたものを一つの種類と数える。
2. それぞれの種類を、効く範囲でいちばん高い段で直す。段は上から、アーキテクチャ、型、lintやCIの検査、テスト、文書の順です。

| 段 | やること（`/correct`の記述） |
| --- | --- |
| アーキテクチャ | 状態の持ち主を一つにする。やり方を一つにする。内部を隠して、誤ったimportが失敗するようにする。エージェントがコピーしそうな古いやり方と使われていないコードを消す |
| 型 | 悪い状態を書けなくする。それでもコンパイルが通るなら、lintかCIの検査を足す。エラーには、代わりに使うファイルや関数の名前を入れる |
| テスト | ふるまいを確かめる。ふるまいが壊れても通るテスト、内部だけ変えると落ちるテストは直すか消す |
| 文書やルール | 最後に、判断が要ることだけを書く。読み飛ばされても何も失敗しないから |

3. 頻度の高い種類から、一つを一つのコミットで直す。新しい検査が、過去に実際に起きた間違いで失敗することを確かめる。
4. エージェント向けの指示ファイルに、規則と、それを強制しているものを対にした表を保つ。訂正を受けたら、直して規則を足す。規則がすでにあるのに何も強制していなかったなら、それは繰り返しなので、同じ変更の中でいちばん高い段で直す。間違いが起こりえなくなった規則は表から消す。

pstackの原則の一つにも、同じ考えが短く書かれています。同じ指示を二度書いていることに気づいたら、文章を増やすのではなく、lint、実行時の検査、スクリプトとして組み込む。構造で直せるなら構造だけで直す。指示の文章は症状である、というものです。

コメントについては`/no-comments`というskillがあります。READMEによれば、レビューの前にコメントを取り除くためのもので、コメントだけを読み取り専用で調べる補助のエージェントを起動します。「消すな」「変える前に誰々に相談」といった制約を書いたコメントが見つかった場合は、その制約を型、実行時の検査、テスト、lintのどれかに置き換える案を出す、と説明されています。

## エージェントに、自分の仕事を確かめさせる {#verification}

逆三角形の三つ目の層は検証です。Tanさんは、チームのコードレビューが、検証の成果物を見る作業に縮んだと述べました。見るのは動画、スクリーンショット、図、形式検証の結果です。[講演：9:40〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=580s)

### 実行して確かめる

いちばん基本の形は、エージェントが自分でコードを動かせるようにすることです。人の開発者が使うのと同じデバッグの道具を、エージェントにも使わせます。Tanさんは例としてChrome DevTools Protocolを挙げました。

Tanさんのチームの検証用のskillには、二つの部品があります。

一つは「feature map」です。利用者の側から見た、アプリの機能の一覧です。Tanさんはサイトマップのようなものだと説明しました。これがあると、「左のサイドバーのあれ」と言ったときに、エージェントが推測しなくて済みます。人とエージェントが同じ言葉を使えるようになります。

もう一つは専用のCLIです。エージェントがアプリを操作するための命令を、毎回書き捨てるのではなく、決まったコマンドにまとめておきます。使うトークンが減り、CLIそのものをテストできます。スライドには、名前で要素を指定してクリックする、画面の状態を取得する、スクリーンショットを保存する、という三つのコマンドの例が載っていました。[講演：10:02〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=602s)

pstackでは、`/create-verification-skill`がこの部品を生成します。ガイドによれば、このskillは人に質問する前にリポジトリを調べます。利用者が何を触るか、アプリを手元でどう起動するか、何で操作できるか、何がふるまいの証拠になるかを割り出し、コードから分からないことだけを人に聞きます。出力は、プロジェクトの中に置く検証用のskillです。起動、動作確認、操作、証拠、後片づけの手順と、機能ごとに「何をもって動いたと言えるか」を書いたfeature mapが含まれます。生成したskillは、渡す前に一度、起動から後片づけまで通して動くことを確かめる。その確認に失敗したら出力を使わない、と書かれています。

ガイドは、この検証用のskillを一度きりのものではなく基盤として扱うよう勧めています。リポジトリにコミットし、人もエージェントも同じやり方でアプリを操作する。アプリが変わればfeature mapは古くなるので、`/maintain-verification-skill`を少なくとも1日1回、できれば定期実行で回す、という運用です。

エージェントが使いやすいCLIの条件も挙げられています。

- 数の少ない、組み合わせられるコマンド
- 壊すおそれのある操作には`--dry-run`
- 機能を少しずつ見せるサブコマンド
- 代わりに何をすればよいかを言うエラーメッセージ
- 詳しい`--help`
- JSONのような、機械が読める出力

### 形式検証と、UIの性質のテスト

Tanさんのチームは、最近になって形式検証も使い始めました。TLA+で、主要な利用の流れをモデル検査しています。例に挙げたのは、複数の端末とプラットフォームにまたがる通知です。Leanでは、一部のアルゴリズムを証明しています。自作の仮想スクロールのライブラリで、ちらつきや揺れが起きないことを確かめているそうです。Tanさんは、これはまだ試している段階だと断りました。すでにいくつかバグを見つけたが、万能の解決策ではなく、環境に重ねる層の一つとして扱っている、という位置づけです。UIについては、Bombadilというライブラリを使ったプロパティベーステストも始めたと述べています。[講演：10:50〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=650s)

pstackのガイドは、形式検証を使う場面を絞っています。並行処理、再試行、状態機械、パーサーのように、バグの代償が大きく、通常のテストでは不具合が起こる条件まで確かめにくいコードです。`/create-formal-verification-skill`は、性質を一つだけ検証します。そのとき、わざと壊したコードでその性質が破られることも示します。失敗するところを見たことのない検査は何も証明しない、という理由です。合格が意味するのは、モデルや定めた範囲の中で成り立つということで、システム全体の保証ではない、とも書かれています。

講演で紹介された`/statechart`は、検証したモデルから、利用者に見える状態の図を描くskillです。ふるまいを決める立場の人が、仕様書を読む代わりに図で確かめられるようにする、という用途です。

### トークンの大半は検証に

Tanさんは、ほかのエンジニアの投稿を引いて、検証の比重を説明しました。その人は半年前、AIが作ったPRに見つけにくいバグが混ざるため、エージェントを信頼できないと書いていた。半年後には、1日に使うトークンの70％が検証に向かっていると書いている。Tanさん自身も、トークンの大半を検証に使っていると述べました。[講演：11:51〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=711s)

Tanさんが強調したのは、そこで使われている技法に新しいものはない、という点です。どれも以前からあるソフトウェア工学の道具で、ただ、理解し、書き、保守する費用が高すぎて使いにくかった。エージェントがその費用を大きく下げた。だからいまは、テストと検証の黄金期の入口にいる、というのがTanさんの見方です。

## pstack：日々の進め方 {#workflow}

ここからは、pstackのREADMEとガイドに書かれた手順です。pstackはCursor向けのプラグインとして配布されていて、MITライセンスです。筆者が読んだ時点の版は0.15.42でした。READMEには、Claude Codeで使う手順も載っています。ただし、一部のskillは別のプラグインに入っていて、Cursorだけの機能を使う手順はClaude Codeでは飛ばされる、とも書かれています。

### 入れ方と、モデルの割り当て

READMEによる導入の手順は、Cursorではチャットで`/add-plugin pstack`を実行する、というものです。Claude Codeでは、`/plugin marketplace add cursor/plugins`でマーケットプレイスを追加し、`/plugin install pstack@cursor-plugins`で入れます。Claude Codeではプラグインのコマンドに接頭辞が付くので、`/poteto-mode`は`/pstack:poteto-mode`になります。Claude Codeの公式ドキュメントにある、公式以外のマーケットプレイスは先に追加する、`/plugin install プラグイン名@マーケットプレイス名`で入れる、という形式と合っています。

入れたあとにすることは二つだけだとREADMEは言います。`/setup-pstack`でモデルを選ぶことと、厳密さが要る作業の最初に`/poteto-mode`を付けることです。

`/setup-pstack`は、使えるモデルを調べ、推論にかける予算を聞き、役割ごとにどのモデルを使うかを決めます。役割には、コードを書く委任先、判断、レビューのパネル、並列の作業者などがあります。結果は小さなルールファイルに書かれ、pstackのすべてのskillがそれを読みます。ガイドは、この設定を反映するために、設定のあとで新しいチャットを始めるよう案内しています。READMEは、モデルごとに強みと弱みがあるので、複数のモデルを組み合わせる作りにしている、と説明しています。

設定の最後に、`/setup-pstack`はプロジェクトに検証の手段があるかを調べ、なければ前の節の検証用skillの生成を一度だけ提案します。ガイドは、初めてなら受けるよう勧めています。自分の仕事を確かめられるエージェントは、検査が通るまで続ける。確かめられないエージェントは、結果をすべて人に返して手で確かめさせる、という理由です。

費用についての注意もあります。pstackは補助のエージェントやレビューのパネルに余分なトークンを使います。抑えたいときは、予算を小さくする、役割に安いモデルを割り当てる、パネルの人数を減らす、小さく明らかな編集には`/poteto-mode`を使わない、といった方法が挙げられています。

### 入口は一つ：`/poteto-mode`

`/poteto-mode`は、依頼を読んで、23のplaybook（手順書）の中から合うものを選びます。選んだplaybookの手順は、そのままやることリストの先頭に写されます。手順を飛ばした場合も、飛ばした理由つきでリストに残ります。何をしなかったかが見える作りです。

playbookには、調査、バグ修正、性能の問題、機能の追加、リファクタリング、試作、見た目の一致、PRを開く、PRをマージできる状態まで面倒を見る、検証してからマージする、長い作業を止めずに進める、前の作業を引き継ぐ、安全に中断する、といったものがあります。

ガイドは、よい依頼文に入れるものを五つ挙げています。

| 入れるもの | 例（ガイドの説明） |
| --- | --- |
| 目標 | 何が悪いのか、何がほしいのか |
| 終わったと言える条件 | 合格か不合格かを判定できるもの。「よくして」「1時間やって」は条件にならない |
| 見たい証拠 | 実際のコマンドの出力、操作の動画、保存された値、前後の数値 |
| すでに分かっていること | 症状、再現の手順、ログの一行 |
| 本当の制約 | 「先に再現して」「まだコードは変えないで」「ふるまいは一切変えない」 |

逆に、入れないほうがよいものも二つあります。一つは、やり方です。何を達成するかを言い、道筋はエージェントに任せます。使うskillを順に並べて指定するのも避けます。playbookがすでに順序を決めていて、手で書いた順序はたいてい手順を落とすからです。もう一つは、原因についての自分の推測です。最初に推測を言うと、エージェントの探す範囲がそこに狭まります。

込み入った報告を渡すときは、最初の一歩を言い直しにします。エージェントに、問題を自分の言葉で言い直させ、コードはまだ変えさせません。読み違いは言い直しの段階で見つかり、直す費用は、間違った修正一つではなく、メッセージ一通で済みます。

READMEには、計画のためのskillがない理由も書かれています。Tanさん個人は計画を信じていない、最良の仕様はコードだ、という立場です。計画を禁じているわけではなく、Cursorの計画用のモードと組み合わせることも、`/poteto-mode`に計画を頼むこともできる、とされています。pstackの原則にも、決める前に二つか三つの試作を作って並べて比べる、というものがあります。

### 文脈と記憶の扱い

長いチャットには、前の作業の文脈がたまります。ガイドは、話題を変えるときは「new task」と言うよう勧めています。そう言わないと、機能追加の途中のエージェントは、新しい質問を次の手順として扱いがちだからです。

文脈の窓については、「文脈の窓を守る」という原則があります。量の多い作業は補助のエージェントに回し、主のチャットには生の出力ではなく要約だけを残す、というものです。

過去の作業を思い出すための仕組みが`/recall`です。記憶は二つの記録にある、とこのskillは説明します。一つは自分のチャットの履歴で、何をして何を決めたかが残っています。もう一つは共有の記録で、ソース管理、課題の管理、チャット、エラーの追跡に、利用者が繰り返し報告している症状や、出荷されて取り消された修正が残っています。`/recall`は、安いモデルの補助エージェントを並列に走らせて両方を調べ、見つかったPRやブランチの現状を実際に確かめたうえで、短い現状のまとめを返します。まとめには、各作業にマージ済み、PRが開いている、作業中、取り消された、といった状態の札を付ける決まりです。

過去の経緯は、指示ファイルだけに書きためるのではなく、チャットの履歴や文書を含む共有の記録から、必要なときに組み立て直します。恒久的に守らせたい規則は、前の節のとおり検査にします。二つは別の役割です。

## 並列に走らせるための分離 {#parallel}

READMEは、pstackの効用を「恐れずに並列化できること」と表現しています。一つのエージェントを深く使って、検証できるよいコードを書くと信頼できるなら、複数を並べても安心できる、という順序です。

並列化の前提は分離です。ガイドによれば、一台の計算機の一つのリポジトリで複数のエージェントを走らせると、作業ツリー、ポート、ビルドの出力を取り合います。いちばんきれいな分離はクラウド上の補助エージェントで、それぞれが自分の仮想マシンとブランチを持ち、依存関係を入れ、アプリを動かし、動画を撮れます。手元で行うなら、作業ごとにブランチとworktreeを分けます。worktreeは増えていくので、マージ済みかどうか、コミットされていない作業があるかを調べて、安全なものだけを消すplaybookも用意されています。

並列の使い方には、三つの型があります。

| skill | 型（READMEとskillの記述） |
| --- | --- |
| `/arena` | 同じ課題に複数の試みを並べ、それぞれのよい部分を取る |
| `/swarm` | 作業を切り分けて複数の作業者に配り、一つの報告にまとめる。終わったと言える条件と、返す成果物を先に決める |
| `/interrogate` | 別々のモデルに、変更を壊す役をさせる。実行して証明できた指摘だけを残す。書式や命名、将来の懸念は報告させない |

三つ目の型には、検証の考え方がよく表れています。レビューの指摘も、実行結果という証拠がなければ採用しません。

役割の分け方にも決まりがあります。`/poteto-mode`を受け取ったチャットが、playbookとやることリストと、補助エージェントの起動を受け持ちます。委任先には専用の種類のエージェントを使い、作業の前にpstackの原則を読ませます。マージの段階では、変更を書いたエージェントと、それを判定するエージェントを必ず別にします。ガイドの言葉では、緑（検査がすべて通っている）は安全と同じではありません。PRを一つずつ、新しいエージェントが実際に動かして確かめ、確かめられたものだけを下から順にマージします。

## 人が離れているあいだの実行 {#overnight}

ガイドの後半は、人が寝ているあいだに作業を進める方法です。その前に満たすべき条件が四つ挙げられています。

- その作業を一度は自分の手でやったか、エージェントがやるのを見ていて、よい結果がどういうものか分かっている
- エージェントが、自分なら使う道具と手がかり（検証用のskill、プロファイラ、ログ）を持っている
- どの段階も自分の仕事を証明でき、基準に届かなければ流れを止められる
- 実行の記録をいくつか読み、繰り返される失敗を道具やskillや検査に変えてある

四つがそろうまでは、見ているあいだだけ回す、というのがガイドの指示です。信頼していないループは、確かめられていない成果物を速く作るだけだからです。

夜に任せるときの依頼文には、目標、終わったと言える条件、許可、抜け道の四つを入れます。ガイドの例では、新しいworktreeで作業すること、古い呼び出しがゼロになりテストが通ることを終わりの条件とすること、判断の記録を残すこと、コミットの前に確認を求めないこと、数時間たっても本当に行き詰まったら止まって理由を書くこと、が数行で書かれています。繰り返しの起動には、Cursorに備わっている`/loop`を使うと説明されています。

時間は終わりの条件にならない、という注意もあります。「4時間やって」と頼むと、エージェントには確かめるものがなく、朝に残るのは4時間分の動きだけです。

ループの中身は単純です。終わりの条件を確かめる。根拠のあるいちばん小さな変更をする。実物で確かめる。進んでいればコミットし、進んでいなければ捨てる。判断を一行、記録する。これを繰り返します。行き詰まったら方針を変え、終わりの条件をこっそり緩めて成功を宣言することはしません。

朝の確認のために、`/show-me-your-work`が判断の記録を残します。時刻、段階、判断、理由、証拠の場所、結果を一行ずつ、タブ区切りのファイルに書きます。人が読むのは一晩分の全部ではなく、判断の一覧です。まとめを返す前に、別の系統のモデルが記録を読み、人が注意して見るべき点を挙げる、とも書かれています。

許可については、「人を待って止まらない」という原則があります。取り消せる作業（コードを書く、作業を分ける）は確認を求めずに進め、結果を見せて、あとから人が直す。取り消せない作業（強制プッシュ、本番のデータの削除、外部への送信）は確認を求める。製品の方向は人が決める、という線引きです。

作業が一つではなく列になっている夜のために、三つのplaybookがあります。独立したPRの列をマージまで運ぶもの、マージはせず検証済みのPRを朝に人へ渡すもの、数日にわたる計画を一つの調整役のチャットに持たせるものです。調整役は、どのエージェントに何をさせるかを決め、成果物を確かめ、自分ではコードを書きません。

講演の最後に、Tanさんはこの先の姿を一つ見せました。新しい版を切り出すたびに、Grok Botが自動で作業を立ち上げ、アプリを実際の利用者のように操作してバグを探し、見つけたバグごとに修正のPRを開き、自動でマージする、というものです。Tanさんは、それができるのは、コードベースがよく、PRが何もしなくてもよいものになるからだ、と説明しました。[講演：16:05〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=965s)

Tanさんが強調したのは順序です。工場を作る前に、まず内側のループを直す。エージェントを訂正するときは、コードベースの改善から始める。lintで新しい発生を止め、古いものを片づける。検証を確かなものにする。内側のループが粗いものを出すなら、それを自動化しても粗いものが増えるだけで、トークンをいくらつぎ込んでも足りなくなる。土台ができていれば、その上に自動化を組むのは難しくない、というのが講演の締めくくりでした。[講演：15:11〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=911s)

## 講演で示された数字と、その読み方 {#results}

Tanさんが成果として示した数字は、次のとおりです。どれもTanさんのスライドと発言によるものです。チームの推移は2026年6月から10月、性能は公開時との比較で、項目によって期間が違います。

| 項目 | Tanさんが示した値 |
| --- | --- |
| Tanさん個人のPR | 10月に約3,000件 |
| チームがマージしたPR | 10月に約1万1000件。6月は約800件 |
| クライアントの安定版 | ほぼ1日に1回 |
| 10月に1件以上PRを出した人 | 約227人。中心のチームのほか、文脈をあまり持たない人も含む |
| 取り消されたコミットの割合 | 6月の約1％から下がり、約0.5％で安定 |
| アプリの性能 | 起動、入力、チャットを開く、切り替える、のどれも公開時より速くなった |

[講演：13:32〜](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=812s)

読むときに気をつけたい点を、筆者の考えとして挙げます。

PRの件数は、品質の指標ではありません。Tanさん自身、pstackのREADMEで、行数を増やすことは目標ではなくむしろ逆で、少なく、質の高いコードを書くためのものだと書いています。講演で品質の側の証拠として出されたのは、取り消しの割合と性能です。取り消しの割合は、取り消されたコミットの割合です。取り消しに至らなかった不具合や、品質の全体を直接測る数字ではありません。

これらは一つのチームの、本人による報告です。チームは枠組みを自分たちで作り、lintの規則を書き、検証の道具を整えてきました。Tanさんが述べたとおり、そこまでに6か月かかっています。同じ数字が別のコードベースで出るかどうかは、講演からは分かりません。

形式検証については、Tanさんが自分で、まだ試している段階だと述べています。

## 自分の環境に移すなら {#apply}

以下は、講演とガイドが勧める順序を、筆者が小さなプロジェクト向けに整理した実践案です。

1. **繰り返している訂正を書き出す。** エージェントに同じことを二度言ったら、それを一つの種類として数える。`/correct`の最初の手順と同じです。
2. **それぞれを、いちばん高い段で直せないか考える。** 構造で起こらなくできるか。型で書けなくできるか。lintで止められるか。指示ファイルに書くのは、どれもできないときだけにする。
3. **lintのエラーメッセージに、代わりのやり方を書く。** エージェントはエラーを読んで直します。何が悪いかだけでなく、どのファイルのどの関数を使うかまで書く。
4. **エージェントが自分で動かして確かめる手段を一つ作る。** 起動の手順、操作の手順、証拠の残し方を決める。機能の一覧と、それぞれの「動いたと言える条件」を書いておく。
5. **依頼文に、終わったと言える条件と、見たい証拠を入れる。** 動画、スクリーンショット、コマンドの出力など、あとで自分が見て確かめられるものを求める。
6. **並列化と自動化は、そのあとにする。** 一つのエージェントの結果を信頼できるようになってから、worktreeや別の計算機で分けて並べる。

応急処置を残すと、それが次のエージェントの手本になって広がります。一つのタイマーが5週間あまりで183個に増えたというTanさんの例は、その危険を示しています。筆者がそこから受け取ったのは、エージェントに言い聞かせる前に、まず手本になるコードのほうを直す、という順序です。
